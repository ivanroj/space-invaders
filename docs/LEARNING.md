# Учебный маршрут

Четыре темы из задания, для каждой указано, что читать и что попробовать
сделать самому. Порядок от простого к сложному.

## 1. Как Go становится WebAssembly

Читать: `build.sh`, первые 30 строк `cmd/wasm/main.go`, функцию `loadEngine` в
`web/wasm.js`.

Что заметить:

- `GOOS=js GOARCH=wasm` — это обычная кросс-компиляция, как под Linux или
  Windows.
- Программа на Go в браузере — это `main()`, которая не завершается: в конце
  стоит `select {}`. Если `main` вернётся, все экспортированные функции
  перестанут работать.
- `wasm_exec.js` даёт модулю то, чего в WebAssembly нет: время, случайные
  числа, доступ к объектам JS.
- `instantiateStreaming` компилирует модуль, пока он скачивается. Для этого
  сервер обязан отдать `Content-Type: application/wasm`.

Задания:

1. Соберите модуль без `-ldflags="-s -w"` и сравните размер. Затем сожмите
   оба файла `gzip -9` и сравните ещё раз.
2. Отдайте `main.wasm` через `python3 -m http.server` и посмотрите во вкладке
   Network, чем отличается загрузка.
3. Добавьте в API функцию `version()`, которая возвращает строку, и вызовите
   её из консоли браузера.

## 2. Мост между Wasm и страницей

Читать: `cmd/wasm/main.go` целиком, `web/wasm.js`, функцию `frame` в
`web/app.js`.

Что заметить:

- `js.FuncOf` превращает функцию Go в функцию JS. Аргументы приходят как
  `[]js.Value`.
- Вызов через границу заметно дороже обычного вызова. Поэтому за кадр он
  один, а данные идут пачкой: 307 200 байт картинки и 64 числа состояния.
- Буферами владеет JS. Go копирует в них через `js.CopyBytesToJS`. Обратный
  вариант (JS читает память Go напрямую) быстрее, но в Go память может
  переехать при росте кучи.
- Индексы полей состояния объявлены один раз в Go и переданы в JS, а не
  продублированы.

Задания:

1. Добавьте в состояние число живых захватчиков и покажите его в блоке «Под
   капотом».
2. Измерьте в консоли, сколько занимает `engine.frame`. Сравните с 16,7 мс,
   которые есть на кадр.
3. Перенесите вызов `putImageData` в Go через `js.Global()` и сравните
   скорость.

## 3. Игровой движок

Читать по порядку: `internal/sim/consts.go`, `game.go` (функция `Step`),
`formation.go`, `bunker.go`, `boss.go`, затем `internal/render/draw.go`.

Что заметить:

- `Step` — единственная функция, которая меняет игру. Один вызов — один такт
  в 1/60 секунды.
- Строй захватчиков двигается как одно целое: хранится смещение строя, а не
  координаты каждого. Чем меньше осталось врагов, тем короче пауза между
  шагами.
- Столкновение прямоугольников — это четыре сравнения (`overlap` в
  `game.go`). Для бункера после него идёт проверка по пиксельной маске.
- Координаты хранятся умноженными на 256. Так получается дробная скорость без
  `float`, а результат одинаков на любом процессоре.
- `sim` ничего не знает о `render`. Связь только через список событий.

Задания:

1. Добавьте шестой бонус, например пробивающий выстрел.
2. Добавьте боссу четвёртую схему атаки.
3. Запустите `go test ./internal/sim -run Deterministic -v`, затем замените
   в одном месте целое деление на `float64` и объясните, почему на вашей
   машине тест может по-прежнему проходить, а полагаться на это нельзя.

## 4. JWT и таблица рекордов

Читать: `internal/server/auth.go`, `scores.go`, `web/api.js`, затем
`internal/server/server_test.go`: тесты читаются как список атак.

Что заметить:

- JWT состоит из трёх частей в base64. Содержимое не зашифровано: откройте
  блок «Под капотом» после входа, там показаны поля вашего токена. Подпись
  защищает от изменения, а не от чтения.
- Алгоритм подписи закреплён на сервере. Если брать его из заголовка токена,
  злоумышленник поставит `alg: none`.
- Access-токен живёт в переменной JS и пропадает при перезагрузке. Refresh
  лежит в cookie `HttpOnly`, скрипты страницы прочитать его не могут.
- У каждого вида токена свой `aud`. Иначе refresh-токен можно было бы
  предъявить как access, а билет на игру — как любой из них.
- Поле `ver` позволяет отозвать токены: при выходе сервер увеличивает версию
  пользователя, и все старые токены перестают приниматься.
- Аутентификация не защищает от нечестного счёта. Защищает то, что сервер
  считает счёт сам.

Задания:

1. Скопируйте access-токен, измените в нём имя пользователя и отправьте
   запрос через `curl`. Объясните ответ.
2. Отправьте одну и ту же запись дважды.
3. Найдите тест, который проверяет, что нельзя прислать запись, записанную
   быстрее реального времени. Зачем эта проверка, если запись всё равно
   переигрывается?
4. Замените хранилище в JSON-файле на SQLite, не меняя тесты.
